# 포즈 조작 Subway Surfers 설계

작성일 2026-07-15

## 개요

노트북 카메라로 사용자의 몸을 추적해 조작하는 3레인 엔드리스 러너다. 사용자가 실제로 좌우로 걸으면 캐릭터가 레인을 옮기고, 실제로 뛰면 점프하고, 실제로 쪼그리면 슬라이드한다. 로컬에서 가볍게 돌려보는 것이 목표이며 배포는 범위 밖이다.

## 확정된 제약

| 항목 | 결정 |
|---|---|
| 카메라 범위 | 전신. 사용자가 1.5~2m 떨어져 선다 |
| 렌더링 | Canvas 2D + 가짜 원근법. 도형 기반, 에셋 없음 |
| 포즈 인식 | MediaPipe Pose Landmarker (tasks-vision) |
| 게임 내용 | 장애물 + 코인. 점수는 주행 거리 + 코인×10 (아래 정의) |
| 저장 | Google Sheets에 랭킹 보드만 |
| 백엔드 | Django. 엔드포인트 3개 |
| 테스트 | `?test=1` 셀프 테스트 + Django pytest |

전신 모드는 사용자가 2m 뒤에서 노트북 화면을 봐야 한다는 뜻이다. 실사용 시 외부 모니터나 TV 미러링을 권장하지만, 코드가 요구하는 사항은 아니다.

## 단일 파일 제약의 정확한 범위

"프론트는 index.html 하나"의 해석은 **직접 작성하는 코드가 전부 index.html 안에 있고 별도 js/css 파일로 쪼개지 않는다**는 것이다. MediaPipe는 수 MB짜리 모델 가중치를 쓰므로 `<script src>`와 모델 URL로 CDN에서 불러온다. 완전 자급자족 단일 파일은 물리적으로 불가능하다.

이 제약의 파급 효과가 하나 있다. JS를 밖에서 import할 수 없어 일반적인 테스트 러너를 붙일 수 없다. `?test=1` 셀프 테스트는 이 제약을 우회하기 위한 선택이다.

Django가 index.html을 직접 서빙한다. 프론트와 API가 같은 오리진이 되어 CORS 설정이 불필요하고, `localhost`는 보안 컨텍스트라 `getUserMedia`가 동작한다.

새로 만드는 소스 파일마다 첫 줄에 역할을 설명하는 한국어 한 줄 주석을 단다.

## 프론트엔드 모듈 경계

index.html은 한 파일이지만 논리적으로 세 덩어리로 나눈다. 각 덩어리는 인접 덩어리의 내부를 모른다.

### PoseTracker

카메라 스트림을 열고 MediaPipe에 프레임을 넣어 랜드마크 33개를 내보낸다. 게임의 존재를 모른다.

- 입력 — `getUserMedia` 비디오 스트림
- 출력 — 프레임마다 `landmarks[]` 또는 `null`(포즈 유실)
- 의존 — MediaPipe tasks-vision

### InputMapper

랜드마크를 받아 조작 신호로 바꾼다. 캘리브레이션 기준선을 소유한다. 카메라도 게임도 모른다.

- 입력 — `landmarks[]`
- 출력 — `{lane: 0|1|2, jump: bool, slide: bool, warning: string|null}`
- 의존 — 없음. 거의 순수 함수

### Game

조작 신호만 받아 상태를 굴리고 Canvas에 그린다. 포즈의 존재를 모른다.

- 입력 — `{lane, jump, slide}`
- 출력 — Canvas 렌더, 게임오버 시 최종 점수
- 의존 — 없음

**이 경계를 고집하는 이유가 실용적이다.** Game이 포즈를 모르므로 키보드로 동일한 신호를 주입할 수 있다. 게임 로직을 수정할 때마다 2m 뒤로 물러나 점프할 수는 없어서, 화살표 키 폴백은 개발 편의 기능이 아니라 필수 인프라다. InputMapper도 랜드마크 시퀀스를 넣으면 판정이 나오는 순수 함수에 가까워 카메라 없이 테스트할 수 있다.

## 포즈 판정 로직

### 좌표계

MediaPipe는 x, y를 0~1로 정규화해 주며 **y는 아래로 갈수록 커진다.** 화면에서 위로 올라간다는 것은 y가 작아진다는 뜻이다. 부호 반전은 이런 코드에서 가장 흔한 버그이므로 변수명에 방향을 명시한다.

### 사용하는 랜드마크

| 인덱스 | 부위 | 용도 |
|---|---|---|
| 2, 5 | 좌/우 눈 | 슬라이드 판정 기준 |
| 11, 12 | 좌/우 어깨 | 몸통 길이 상단 |
| 23, 24 | 좌/우 엉덩이 | 몸통 길이 하단, 레인 판정 기준 |
| 27, 28 | 좌/우 발목 | 점프 판정 기준 |

좌우 쌍은 중점을 사용한다.

### 스케일 정규화

픽셀 값을 그대로 임계값과 비교하면 사용자가 카메라에 가까워질 때 판정이 깨진다. 어깨 중점과 엉덩이 중점 사이 거리를 몸통 길이로 정의하고, 모든 변화량을 이 값으로 나눈다. 거리가 변하면 몸통 길이도 같이 변하므로 비율은 유지된다.

```
몸통길이   = |어깨중점y - 엉덩이중점y|
점프량     = (기준_발목y - 현재_발목y) / 현재_몸통길이     // 발목이 뜨면 양수
슬라이드량 = (현재_눈y   - 기준_눈y)   / 현재_몸통길이     // 머리가 내려가면 양수
```

### 캘리브레이션과 기준선 추종

시작 카운트다운 5초 동안 선 자세의 발목 y, 눈 y를 평균 내어 기준선으로 삼는다.

기준선은 고정하지 않는다. 사용자가 게임 중 앞뒤로 조금씩 움직이면 고정 기준선은 서서히 틀어진다. 점프도 슬라이드도 아닌 것이 명백한 프레임 — 두 변화량이 모두 임계값의 절반 아래 — 에서만 기준선을 현재 값 쪽으로 느리게 EMA로 끌어당긴다.

**판정 중에는 절대 갱신하지 않는다.** 이 가드가 없으면 슬라이드 자세가 기준선으로 굳어버려 슬라이드가 영영 안 먹는다.

### 레인 판정

**미러링이 핵심이다.** 웹캠 원본은 거울이 아니다. 사용자가 자기 왼쪽으로 이동하면 이미지 x는 오히려 커진다. `laneX = 1 - x`로 뒤집고, 카메라 프리뷰도 CSS `transform: scaleX(-1)`로 반전해 보여준다. 그래야 사용자가 왼쪽으로 갈 때 프리뷰 속 자기도 왼쪽, 캐릭터도 왼쪽으로 일치한다.

기준점은 코가 아니라 **엉덩이 중점 x**를 쓴다. 머리는 움직일 때 흔들려 레인이 떨린다.

경계 떨림은 히스테리시스로 막는다. 나갈 때와 들어올 때 경계를 다르게 둔다.

| 전이 | 조건 |
|---|---|
| 가운데 → 왼쪽 | laneX < 0.30 |
| 가운데 → 오른쪽 | laneX > 0.70 |
| 왼쪽 → 가운데 | laneX > 0.36 |
| 오른쪽 → 가운데 | laneX < 0.64 |

### 스무딩

신호마다 다르게 건다.

- **레인 x** — EMA를 세게 건다. 안정성이 중요하고 한두 프레임 지연은 체감되지 않는다.
- **발목 y** — 스무딩을 거의 걸지 않는다. 점프는 짧고 빠른 순간 신호라 스무딩하면 봉우리가 뭉개져 감지 자체가 안 된다.

### 트리거 방식

점프와 슬라이드 모두 트리거식이다. 임계값을 넘는 상승 엣지에서 감지하고, 그 뒤엔 포즈와 무관하게 600ms 고정 애니메이션이 돈다. 애니메이션 종료 후 300ms 더 잠가 한 번의 물리적 점프가 두 번으로 세지는 것을 막는다.

슬라이드를 유지식으로 하면 쪼그린 자세를 계속 버텨야 해 금방 지친다.

### 임계값

시작값이며 실측으로 튜닝해야 한다.

| 항목 | 시작값 |
|---|---|
| 점프 | 0.2 몸통 |
| 슬라이드 | 0.5 몸통 |
| 기준선 추종 EMA alpha | 0.02 |
| 레인 x EMA alpha | 0.3 |
| 애니메이션 지속 | 600ms |
| 불응기 | 300ms |

**이 값들은 몸으로 해보기 전에는 맞을 수 없다.** 그래서 디버그 패널이 설계에 포함된다.

### 디버그 패널

화면 구석 오버레이. 현재 점프량, 슬라이드량, laneX, 확정 레인, 각 랜드마크 visibility가 실시간으로 표시되고 임계값을 슬라이더로 즉시 조정한다.

이것은 speculative한 기능이 아니라 튜닝의 전제 조건이다. 없으면 숫자 수정 → 새로고침 → 뒤로 물러나기 → 뛰어보기를 수십 번 반복해야 한다.

### visibility 처리

MediaPipe가 랜드마크마다 주는 visibility가 0.5 아래로 떨어지면 경고 배너를 띄우고 점프 판정을 끈다. 보이지 않는 발목의 추정 좌표로 판정하면 아무 때나 점프가 터진다.

**미확인 사항이 하나 있다.** tasks-vision 버전에 따라 visibility가 채워지지 않는다는 보고가 있다. 구현 첫 단계에서 이 값이 실제로 오는지 확인한다. 오지 않으면 발목 y가 프레임 안(0 < y < 1)에 있는지로 대체한다.

## 게임 루프

장애물과 코인은 소실점에서 생성되어 z가 줄며 다가온다. z를 화면 y와 크기로 투영하면 멀리서 작게 생겨 커지며 내려온다.

캐릭터는 레인 인덱스 0·1·2를 갖되 화면 x는 부드럽게 보간한다. 레인 판정이 순간이동해도 화면에서는 미끄러지듯 움직인다.

### 장애물 종류

| 종류 | 해소 동작 |
|---|---|
| 낮은 바리케이드 | 점프 |
| 높은 가로보 | 슬라이드 |
| 기둥 | 레인 변경 |

### 충돌 판정

z가 캐릭터 근처 구간에 진입했을 때 레인이 같은지 확인하고, 같으면 현재 상태가 해당 장애물을 해소하는지 본다. 코인은 동일한 판정을 재사용하되 결과만 점수 가산으로 바꾼다.

속도는 시간에 따라 완만히 상승한다. 충돌 시 즉시 게임오버다.

### 스폰 제약

**게임이 항상 클리어 가능해야 한다.** 규칙 없이 무작위로 뿌리면 세 레인에 기둥이 동시에 떠서 피할 수 없는 상황이 만들어진다.

- 한 스폰 그룹에 기둥은 최대 2개다. 최소 한 레인은 반드시 비어 있다
- 기둥과 점프·슬라이드 장애물이 세 레인을 동시에 막지 않는다. 통과 가능한 레인 또는 동작이 항상 하나 이상 존재한다
- 연속한 스폰 그룹 사이에는 최소 반응 시간을 보장하는 z 간격을 둔다. 속도가 올라가면 z 간격도 함께 벌려 반응 시간을 일정하게 유지한다
- 코인은 통과 가능한 레인에만 배치한다. 코인이 플레이어를 함정으로 유인하지 않는다

### 점수 정의

점수 단위를 명시한다. 랭킹에 그대로 올라가는 숫자다.

```
점수 = floor(누적_z_이동량) + 코인_개수 × 10
```

누적 z 이동량은 프레임마다 `속도 × 델타타임`을 더한 값이다. 속도가 오르면 같은 시간에 점수가 더 빨리 쌓여, 오래 버틸수록 보상이 커진다.

### 화면 전환

2m 뒤에서는 키보드도 마우스도 쓸 수 없다. 그래서 조작이 필요한 단계는 전부 시작 화면에 모은다.

1. 시작 화면 — 앉아서 닉네임 입력, TOP 10 확인, 시작 버튼 클릭
2. 카운트다운 5초 — 물러나서 자세 잡기. 이 동안 캘리브레이션 수행
3. 플레이
4. 게임오버 — 점수 자동 전송 후 시작 화면 복귀

## 백엔드

### 엔드포인트

| 메서드 | 경로 | 동작 |
|---|---|---|
| GET | `/` | index.html 렌더 |
| GET | `/api/scores/` | 시트에서 상위 10개를 점수 내림차순으로 반환 |
| POST | `/api/scores/` | 닉네임·점수·시각 한 줄 append |

### Google Sheets

gspread와 서비스 계정 키를 사용한다. 워크시트 칼럼은 `nickname | score | played_at`이다.

같은 오리진이므로 CSRF 토큰은 템플릿에서 직접 꺼내 쓴다.

### 검증 범위

닉네임 길이 제한(12자)과 점수 정수 검증만 둔다. **클라이언트의 점수 조작은 막지 않는다.** 로컬에서 혼자 돌리는 장난감에 서버 사이드 검증을 넣는 것은 배보다 배꼽이다. 이것은 의도적인 생략이지 누락이 아니다.

## 에러 처리

**원칙 — 시트는 부가 기능이고 게임이 본체다. 시트 때문에 게임이 죽으면 안 된다.**

| 상황 | 처리 |
|---|---|
| 카메라 권한 거부 | 안내 후 키보드 모드로 진행 |
| MediaPipe 로드 실패 | 안내 후 키보드 모드로 진행 |
| 포즈 유실 | 마지막 입력 유지 + 경고 배너 |
| 발목 visibility 낮음 | 경고 배너 + 점프 판정 비활성 |
| 점수 전송 실패 | 토스트로 알리고 진행 |
| 랭킹 조회 실패 | 해당 자리에 "불러올 수 없음" 표시 |

## 테스트

### InputMapper — `?test=1` 셀프 테스트

index.html에 `?test=1`로 접속하면 합성 랜드마크 시퀀스를 넣는 테스트가 돌고 결과를 화면에 출력한다. 단일 파일 제약 때문에 외부 러너를 못 붙이는 것에 대한 우회다.

케이스는 다음과 같다.

- 점프 시퀀스에서 jump가 정확히 1회 발화한다
- 슬라이드 시퀀스에서 slide가 정확히 1회 발화한다
- 레인 이동이 좌·중·우로 올바르게 판정된다
- 경계에서 미세하게 흔들 때 레인이 떨리지 않는다
- 사용자가 앞뒤로 움직여 스케일이 변해도 판정이 유지된다
- 발목 visibility가 낮으면 점프가 발화하지 않는다

### Django API — pytest

gspread를 모킹해 엔드포인트를 덮는다.

- `GET /api/scores/`가 상위 10개를 점수 내림차순으로 반환한다
- `POST /api/scores/`가 시트에 행을 추가한다
- 닉네임 길이 초과가 거부된다
- 시트 예외가 게임을 죽이지 않고 에러 응답으로 변환된다
